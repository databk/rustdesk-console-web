## 旧协议风险与发布验收

最初的旧版兼容目标为 RustDesk 1.4.9 及其 hbb_common 提交 7e1c392c62d39c364127307cd408421dd5f8cfb0。该提交的 src/tcp.rs 中，Encrypt 保存一个对称密钥和两个初值为零的计数器。enc、dec 分别先递增计数器，再使用相同的小端序 nonce 构造，因此两个方向的第一条加密消息都会在同一密钥下使用序号 1。浏览器协商到旧版 KX 0 时仍遵循这一通信约定；KX 1 则使用独立的双向密钥。

Libsodium secretbox 要求同一密钥下每条消息的 nonce 唯一。仅使用合成密钥和明文的确定性测试表明，两个方向首条密文正文的异或结果等于对应明文的异或结果，证实兼容实现存在密钥流复用。能够观察双向内层密文的一方可能推断明文关系；已知明文还可能暴露另一方向的对应字节。该测试不代表已完成真实攻击、任意解密或密钥恢复。

证据：

- 固定版本的一手源码：https://github.com/rustdesk/hbb_common/blob/7e1c392c62d39c364127307cd408421dd5f8cfb0/src/tcp.rs#L278-L300；nonce 构造位于第 190–193 行。
- 密码学使用要求：https://doc.libsodium.org/secret-key_cryptography/secretbox。
- 原生客户端 1.4.9 握手：https://github.com/rustdesk/rustdesk/blob/1.4.9/src/server.rs#L184-L225；这里解封装交换密钥并交给同一流加密器，没有拆分双向密钥。
- 本地复现：src/features/web-client/core/crypto.test.ts 中名为 “documents the pinned protocol cross-direction nonce collision for release review” 的测试。这是明确的风险演示，测试通过不代表满足安全属性。

审查范围限于上述固定版本源码及本次检查的浏览器兼容代码，未审计所有已发布原生二进制，也未证明各类部署拓扑下的可利用性。这不是 CVE 编号认定，也不是声称发现了新的上游漏洞。WSS 保护其 TLS 传输链路，但不会修复内层加密构造，也不能据此证明可防范能看到内层密文的中继。

**以下为审查当天的历史调查状态：** 当时通过 git ls-remote 和不可变源码地址确认，hbb_common main 提交 94ec710894ecd548b4fe174ef781eca5c1a318c0 提供 KX_VERSION_LATEST = 1、方向密钥派生和握手上下文绑定，分别使用发送与接收密钥。此时它只是具体的修复候选，尚不能证明浏览器或已安装原生程序实际使用了该机制。当时官方最新发布页仍指向 1.4.9；采用新方案前需要核实原生集成、降级行为和发布二进制兼容性。该轮调查没有更改依赖包或生成协议的固定版本。

当时的调查来源：https://raw.githubusercontent.com/rustdesk/hbb_common/94ec710894ecd548b4fe174ef781eca5c1a318c0/src/tcp.rs，以及 https://github.com/rustdesk/rustdesk/releases/latest（当时解析为 /releases/tag/1.4.9）。这里的 KX 版本 1 是密码学协商版本，与官方 Web Client V1/V2 产品命名无关。

最初调查建议等待兼容的后续协议再发布。维护者随后批准的策略是协商经过认证的 KX 1，同时保留经过认证的 KX 0，并持续显示不阻塞连接的风险提示；最初一律拒绝旧版的建议已成为历史。不应宣称旧版 KX 0 的端到端保密性已修复或通过独立认证。也不能单方面改变浏览器 nonce 序列、添加方向密钥或降低加密强度：原生对端必须实现一致的协议约定。

最初的调查顺序如下，候选阶段的状态已由下文实现和后续验收取代：

1. 独立审查已确认的原生握手、加密路径和上游方向密钥候选，确定带版本的兼容后继方案；替代方案通过审查前保留固定版本复现。
2. 优先采用具有认证协商与互操作回归覆盖的上游协议、客户端更新。当时候选已存在于源码，但尚未在本浏览器实现，也未对兼容的已发布原生二进制完成验证。
3. 如果没有兼容修正，继续保持实验性、默认关闭。原生分叉、新隧道或网关会改变已批准的原版客户端架构，需要单独设计决策；普通应用层加固不能修复这一协议问题。

### 浏览器实现（2026-09-30，Asia/Shanghai）

生产协议生成器固定 rustdesk@4812a9815bd3c6a93f3ad903f29504168c4930a1 和 hbb_common@229b904508364c8997aad0fb5af57effac859f60，并验证两个协议输入及固定父项目许可证的哈希。通过保留的历史协议定义核对旧字段编号与类型。

verifyIdentity 返回经过认证的公钥和 KX 声明。RemoteSession 只依据对端签名的会话声明选择版本，忽略协调服务身份信息中的 KX 元数据及展示用版本字符串。KX 1 使用上游带密钥 BLAKE2b 握手上下文派生，双方发送、接收密钥方向相反；经过签名的声明缺失版本或版本为零时保留 KX 0。临时密钥、根密钥及派生字节缓冲区在成功或失败时清零；释放加密器时清除保留的两个方向密钥。这不能保证浏览器管理的所有副本均被擦除。

协商版本通过带会话代次的安全事件传递。旧版会话在认证期间、连接界面和全屏界面持续显示不阻塞操作的警告；提交密码或收到对端信息不会清除警告。断开、崩溃、替换配置或账户、重新连接时清除状态，过期事件不能重新恢复它。无效身份、签名及 v1 解密失败均终止连接，不重试旧版。

该实现阶段的 11 个测试套件、76 项前端测试通过，其中本次新增 20 项，覆盖四组上游 Rust 已知答案子密钥、签名字段篡改、旧版与当前版本协商及未来版本声明、包括 KDF 失败在内的根密钥与派生缓冲区清理、禁止降级重试，以及 Worker/UI 生命周期。旧加密诊断仍是风险复现，不代表满足安全属性。另有十一项 Node 研究检查，包括逐字段核对旧协议定义。**该阶段尚未进行新增真实浏览器与原生客户端验收，也未执行固定 nightly。** 当时实现和检查代理均在执行前因 encrypted_content 转发错误失败，因此这部分是主会话实现与检查，不是独立审查；后续独立 CLI 审查及真机验收见本文开头链接。

## 资源限制与边界

显示元数据最多允许 16 个显示器，单边尺寸上限为 8192 像素，总像素数上限为 7680 x 4320，坐标起点和终点必须落在有符号 32 位整数范围。这些是防御性上限，不代表已验证的 8K 或多显示器产品支持。既有数据包、队列、解码器和光标限制见 [使用与维护说明](README.md)。

解码帧检查发生在 WebCodecs 已产出帧之后，可防止后续过大的 Canvas 分配和发布，但无法严格限制解码器或 GPU 分配。WebSocket 限制在浏览器交付消息后生效，不能限制每一个浏览器及网络缓冲区。本报告不声称能完全防止拒绝服务攻击。

本轮源码审查未发现需要更改后端认证或配置投影。JWT、会话撤销以及默认关闭配置约定继续由专门的后端测试覆盖。
